== Part 1 -- Beyond All-or-Nothing RBAC

=== Know

_Historically, managing a multicluster fleet with RHACM required broad administrative roles that exposed the entire infrastructure to potential mismanagement. The ClusterPermission API changes this fundamentally by enabling surgical, namespace-scoped permission distribution to managed clusters._

**Business Challenge:**
A VM operations team needs to start, stop, restart, and console into VMs on managed clusters. Today, this requires either:

* *cluster-admin on each managed cluster* -- too broad, exposes the entire cluster
* *Manual Role/RoleBinding creation on each cluster* -- does not scale, drifts over time

Neither option is acceptable for organizations with dozens of clusters and hundreds of VMs.

**Technical Solution:**
The `ClusterPermission` API (`clusterpermissions.rbac.open-cluster-management.io`) allows the Hub to:

1. Define a custom ClusterRole with exact kubevirt.io permissions
2. Automatically distribute the ClusterRole and ClusterRoleBinding to managed clusters
3. Maintain the lifecycle of distributed RBAC via ManifestWork synchronization

**Business Value:**

* *Surgical precision* -- grant exactly kubevirt.io operations, nothing else
* *Lifecycle management* -- permissions are continuously synchronized, not "set and forget"
* *Centralized audit* -- all permission grants are visible on the Hub
* *Group-based targeting* -- bind to a group, not individual users, for scalable team management

=== Show

NOTE: Ensure you are on the **Hub cluster terminal** and logged into OpenShift. If unsure, run `oc whoami` to verify. See xref:02-details.adoc#_connecting_to_clusters[Connecting to Clusters] for setup.

* Review the ClusterPermission manifest before applying:
+
[source,role="execute"]
----
cat rbac/cluster-permission-vm-edit.yaml
----

* Note the key elements:
** `clusterRole.rules` defines exactly which kubevirt.io operations are permitted
** `clusterRoleBinding` creates a ClusterRoleBinding on the managed cluster for the `vm-operators` group
** The subject is a Group (`vm-operators`) -- not individual users, so team membership changes propagate automatically

== Part 2 -- Create a Scoped VM Operator User

=== Know

_To demonstrate the console experience, we create a real user (`vm-operator`) who belongs to the `vm-operators` group. This user gets only the access they need: view managed clusters in ACM and manage VMs on those clusters. They cannot see nodes, secrets, or cluster-level configuration._

=== Show

* Create the `vm-operators` group with a `vm-operator` user:
+
[source,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: vm-operators
users:
  - vm-operator
EOF
----

* Add the `vm-operator` user to HTPasswd authentication so they can log into the console (password: `redhat123`):
+
[source,role="execute"]
----
HTPASSWD=$(oc get secret htpasswd -n openshift-config -o jsonpath='{.data.htpasswd}' | base64 -d)
NEW_ENTRY=$(htpasswd -nbB vm-operator redhat123)
UPDATED="${HTPASSWD}"$'\n'"${NEW_ENTRY}"
echo "$UPDATED" | oc create secret generic htpasswd \
  --from-file=htpasswd=/dev/stdin -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
----

* Grant the user view access to the managed cluster and the virt-clusters ManagedClusterSet in ACM:
+
[source,role="execute",subs="attributes+"]
----
oc adm policy add-cluster-role-to-user view vm-operator

cat <<EOF | oc apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: vm-operator-managed-cluster-view
subjects:
  - kind: User
    name: vm-operator
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: open-cluster-management:view:{student_cluster_name}
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: vm-operator-clusterset-view
subjects:
  - kind: User
    name: vm-operator
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: open-cluster-management:managedclusterset:view:virt-clusters
  apiGroup: rbac.authorization.k8s.io
EOF
----

== Part 3 -- Apply ClusterPermission and Distribute RBAC

=== Know

_ClusterPermission resources are namespaced on the Hub -- the namespace name matches the managed cluster name. When the ClusterPermission is created, ACM generates ManifestWork to distribute the Role and RoleBinding to the target cluster. The permissions are continuously monitored for drift and re-applied if needed._

=== Show

* Apply the ClusterPermission to target `{student_cluster_name}`:
+
[source,role="execute"]
----
oc apply -f rbac/cluster-permission-vm-edit.yaml
----

* Verify the ClusterPermission and ManifestWork were created:
+
[source,role="execute",subs="attributes+"]
----
oc get clusterpermissions -n {student_cluster_name}
oc get manifestwork -n {student_cluster_name} | grep vm-editor
----

* SSH to the managed cluster to confirm the RBAC was distributed:
+
[source,role="execute",subs="attributes+"]
----
{student_1_ssh_command}
----
+
Password: `{student_1_bastion_ssh_password}`

* Verify the ClusterRole grants the expected kubevirt.io permissions:
+
[source,role="execute"]
----
oc get clusterrole vm-editor-permission -o jsonpath='{range .rules[*]}{.apiGroups[*]}{"\t"}{.resources[*]}{"\t"}{.verbs[*]}{"\n"}{end}'
----
+
You should see rules granting `get`, `list`, `watch`, `update`, `patch` for `kubevirt.io` resources and `start`, `stop`, `restart`, `console` subresources.

* Return to the Hub terminal:
+
[source,role="execute"]
----
exit
----

== Part 4 -- The Console Experience: Admin vs. VM Operator

=== Know

_This is the most visual and compelling part of the module. By logging into the ACM console as the `vm-operator` user, you demonstrate exactly what a scoped user sees -- and more importantly, what they do NOT see. This is the "before and after" that resonates with customers._

=== Show

* First, note what you see as the **admin** user in the ACM console:
** Full *Infrastructure* menu with Clusters, Automation, Bare metal assets
** *Governance* with all policies
** *Applications* with all subscriptions and application sets
** Fleet Virtualization showing all clusters and all VMs

* Now open a new **incognito/private browser window** and navigate to the ACM console:
+
----
{openshift_console_url}
----
+
Log in as:
+
** Username: `vm-operator`
** Password: `redhat123`

* Observe the **restricted view** as the `vm-operator` user:
** The *Fleet Virtualization* perspective shows only the clusters and VMs in the `virt-clusters` ManagedClusterSet
** The user can see VM status, access the VM console, and view VM metrics
** The user **cannot** see *Governance* policies, *Infrastructure* node details, or cluster secrets
** The user **cannot** create or delete managed clusters

image::module-07-vm-operator-console.png[VM operator's restricted console view showing only Fleet Virtualization access]

* Click on a VM (e.g., `win2019-install`) and open the *Actions* dropdown to show the available operations:

image::module-07-vm-operator-actions.png[VM operator can Stop Restart Reset and Console into VMs from the Actions menu]

The `vm-operator` user can **Stop**, **Restart**, **Reset**, access the **Console**, and view VM metrics -- exactly the operations defined in the ClusterPermission. They cannot Clone, Delete, or perform Migration actions that require broader permissions.

[TIP]
====
Open the admin console and the vm-operator console side by side to show the contrast. The admin sees the full RHACM feature set; the vm-operator sees only what they need -- Fleet Virtualization for their assigned clusters.
====

* Back in the **Hub terminal**, verify the access boundaries with CLI checks:
+
[source,role="execute"]
----
oc auth can-i get nodes --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

+
[source,role="execute"]
----
oc auth can-i get secrets -n openshift-config --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

+
[source,role="execute"]
----
oc auth can-i delete managedclusters --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

[IMPORTANT]
====
**Key message for the customer:** "This operator can view and manage VMs across the fleet from the console. They can start, stop, restart, and console into any VM on their assigned clusters. But they cannot see a single node, secret, or cluster-level resource. And this permission is centrally managed from the Hub -- if you revoke the ClusterPermission, the RBAC disappears from all managed clusters within seconds. No more manual Role/RoleBinding management on 50 clusters."
====

== Key Takeaways

* ClusterPermission API replaces manual Role/RoleBinding management at scale
* Permissions are continuously synchronized via ManifestWork -- drift is automatically corrected
* VM operators get a full console experience scoped to exactly their responsibilities
* The admin vs. vm-operator console comparison is the most powerful visual in the module
* Group-based subjects mean team membership changes propagate without manifest updates
* Revoking access on the Hub propagates to all managed clusters automatically
