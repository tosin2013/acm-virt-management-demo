== Part 1 -- Enable Fine-Grained RBAC

=== Know

_RHACM 2.17 introduces a dedicated fine-grained RBAC subsystem for virtualization. Before creating role assignments, the `fine-grained-rbac` component must be enabled in the MultiClusterHub resource. This unlocks the MulticlusterRoleAssignment API and the console-based role assignment UI._

**What changed from 2.16:** The `ClusterPermission` API (`v1alpha1`) distributed custom inline rules via ManifestWork. In 2.17, the `MulticlusterRoleAssignment` API (`v1beta1`) replaces this for virtualization RBAC. MRA references existing ClusterRoles by name and uses Placement resources for cluster targeting -- a declarative, scalable model that integrates with the ACM console.

=== Show

NOTE: Ensure you are on the **Hub terminal** and logged into OpenShift. If unsure, run `oc whoami` to verify. If disconnected, reconnect with: `{hub_ssh_command}` (password: `{bastion_ssh_password}`). See xref:02-details.adoc#_connecting_to_clusters[Connecting to Clusters] for full details.

* Enable the fine-grained RBAC component in the MultiClusterHub:
+
[source,role="execute"]
----
INDEX=$(oc get mch multiclusterhub -n open-cluster-management -o jsonpath='{.spec.overrides.components}' | \
  python3 -c "import sys,json; data=json.load(sys.stdin)
for i,c in enumerate(data):
  if c.get('name')=='fine-grained-rbac': print(i); break
else: print(-1)")

if [[ "$INDEX" == "-1" ]]; then
  oc patch mch multiclusterhub -n open-cluster-management --type=json \
    -p='[{"op": "add", "path": "/spec/overrides/components/-", "value": {"name": "fine-grained-rbac", "enabled": true}}]'
else
  oc patch mch multiclusterhub -n open-cluster-management --type=json \
    -p="[{\"op\": \"replace\", \"path\": \"/spec/overrides/components/$INDEX/enabled\", \"value\": true}]"
fi
----

* Verify the component is enabled:
+
[source,role="execute"]
----
oc get mch multiclusterhub -n open-cluster-management -o jsonpath='{.spec.overrides.components}' | python3 -m json.tool
----
+
You should see `"name": "fine-grained-rbac", "enabled": true` in the output.

== Part 2 -- Understand the New RBAC Model

=== Know

_RHACM 2.17 provides specialized roles for fleet virtualization that extend the standard `kubevirt.io` roles installed by the OpenShift Virtualization operator. Permissions are constructed using a combination of hub-level roles (for console access) and spoke-level roles (for VM operations)._

**Hub-level roles** (applied as ClusterRoleBindings on the Hub):

* `acm-vm-fleet:view` -- prerequisite for accessing the fleet virtualization console
* `acm-vm-fleet:admin` -- prerequisite for cross-cluster live migration tasks

**Spoke-level roles** (distributed to managed clusters via MRA):

* `kubevirt.io:view` / `kubevirt.io:edit` / `kubevirt.io:admin` -- standard OpenShift Virtualization roles
* `acm-vm-extended:view` -- extends `kubevirt.io` roles with console visibility for configurations, status, and troubleshooting
* `acm-vm-extended:admin` -- extends `kubevirt.io` roles with administrative troubleshooting and configuration in the console
* `acm-vm-cluster-migration:view` -- enables cross-cluster live migration readiness checks

**The MulticlusterRoleAssignment (MRA) API:**

The MRA custom resource (`rbac.open-cluster-management.io/v1beta1`) provides a declarative method for distributing RBAC across a multicluster environment. Instead of creating one ClusterPermission per managed cluster namespace, you create a single MRA on the Hub that:

1. Specifies a **subject** (User or Group)
2. References one or more **existing ClusterRoles** by name
3. Uses a **Placement** resource to select target clusters
4. Optionally scopes access to specific **namespaces** on those clusters

The system creates the corresponding RoleBinding or ClusterRoleBinding on each selected managed cluster.

== Part 3 -- Create a Scoped VM Operator User

=== Know

_To demonstrate the console experience, we create a real user (`vm-operator`) who belongs to the `vm-operators` group. This user gets only the access they need: view the fleet virtualization console on the Hub and manage VMs on managed clusters. They cannot see nodes, secrets, or cluster-level configuration._

=== Show

* Create the `vm-operators` group with a `vm-operator` user:
+
[source,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: user.openshift.io/v1
kind: Group
metadata:
  name: vm-operators
users:
  - vm-operator
EOF
----

* Add the `vm-operator` user to HTPasswd authentication so they can log into the console (password: `redhat123`):
+
[source,role="execute"]
----
HTPASSWD=$(oc get secret htpasswd -n openshift-config -o jsonpath='{.data.htpasswd}' | base64 -d)
NEW_ENTRY=$(htpasswd -nbB vm-operator redhat123)
UPDATED="${HTPASSWD}"$'\n'"${NEW_ENTRY}"
echo "$UPDATED" | oc create secret generic htpasswd \
  --from-file=htpasswd=/dev/stdin -n openshift-config \
  --dry-run=client -o yaml | oc apply -f -
----

== Part 4 -- Apply Hub-Level and Spoke-Level RBAC

=== Know

_The fine-grained RBAC model requires permissions at two levels: the Hub cluster (for console access) and the managed clusters (for VM operations). We apply both in this step._

**Hub-level:** A ClusterRoleBinding on the Hub granting `acm-vm-fleet:view` to the `vm-operators` group. This is a prerequisite for the group to access the fleet virtualization console.

**Spoke-level:** A MulticlusterRoleAssignment that distributes `kubevirt.io:edit` and `acm-vm-extended:admin` to managed clusters selected by a Placement resource.

=== Show

* Grant the `vm-operators` group view access to the managed cluster and ManagedClusterSet:
+
[source,role="execute",subs="attributes+"]
----
oc adm policy add-cluster-role-to-user view vm-operator

cat <<EOF | oc apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: vm-operator-managed-cluster-view
subjects:
  - kind: User
    name: vm-operator
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: open-cluster-management:view:{student_cluster_name}
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: vm-operator-clusterset-view
subjects:
  - kind: User
    name: vm-operator
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: open-cluster-management:managedclusterset:view:virt-clusters
  apiGroup: rbac.authorization.k8s.io
EOF
----

* Apply the Hub-level fleet view role binding:
+
[source,role="execute"]
----
oc apply -f ~/acm-virt-management-demo/rbac/hub-vm-fleet-view-binding.yaml
----

* Review the Placement that selects virtualization-enabled clusters:
+
[source,role="execute"]
----
cat ~/acm-virt-management-demo/rbac/virt-rbac-placement.yaml
----

* Create the `virt-clusters` namespace and bind the ManagedClusterSet (required for the Placement to resolve clusters):
+
[source,role="execute"]
----
oc create namespace virt-clusters --dry-run=client -o yaml | oc apply -f -

cat <<EOF | oc apply -f -
apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSetBinding
metadata:
  name: virt-clusters
  namespace: virt-clusters
spec:
  clusterSet: virt-clusters
EOF
----

* Apply the Placement:
+
[source,role="execute"]
----
oc apply -f ~/acm-virt-management-demo/rbac/virt-rbac-placement.yaml
----

* Review the MulticlusterRoleAssignment before applying:
+
[source,role="execute"]
----
cat ~/acm-virt-management-demo/rbac/multicluster-role-assignment-vm-edit.yaml
----
+
Note the key elements:
** `spec.subject` targets the `vm-operators` Group -- not individual users
** `roleAssignments` references `kubevirt.io:edit` and `acm-vm-extended:admin` by name (existing ClusterRoles on managed clusters)
** `clusterSelection` uses the Placement resource to dynamically select target clusters
** No inline rule definitions -- the MRA references roles that are already installed by the operators

* Apply the MulticlusterRoleAssignment:
+
[source,role="execute"]
----
oc apply -f ~/acm-virt-management-demo/rbac/multicluster-role-assignment-vm-edit.yaml
----

* Verify the MRA was created:
+
[source,role="execute"]
----
oc get multiclusterroleassignments -n virt-clusters
----

== Part 5 -- Console-Based Role Assignment (Alternative)

=== Know

_RHACM 2.17 also provides a console UI for creating role assignments without writing YAML. This is useful for ad-hoc assignments or for administrators who prefer a graphical workflow._

=== Show

* Open the ACM console at {openshift_console_url} and log in with `{user}` / `{password}` if not already logged in (see xref:02-details.adoc#web-console-login[Logging into the Web Consoles]). Navigate to **Infrastructure** → **Virtual Machines** → **Settings** → **Role Assignments**

* From the Role Assignments tab, you can:
** View all existing role assignments across the fleet
** Create new assignments by selecting an identity (user or group), a role, and target clusters
** Modify or delete existing assignments

* To create an assignment via the console:
. Click **Create role assignment**
. Select the identity type (User or Group) and enter the name
. Choose the role (e.g., `kubevirt.io:edit`)
. Select the target clusters or cluster sets
. Optionally scope to specific namespaces
. Click **Create**

[TIP]
====
The console UI creates the same `MulticlusterRoleAssignment` resources under the hood. You can verify by running `oc get multiclusterroleassignments -A` after creating an assignment in the console.
====

== Part 6 -- The Console Experience: Admin vs. VM Operator

=== Know

_This is the most visual and compelling part of the module. By logging into the ACM console as the `vm-operator` user, you demonstrate exactly what a scoped user sees -- and more importantly, what they do NOT see. This is the "before and after" that resonates with customers._

=== Show

* First, note what you see as the **admin** user in the ACM console:
** Full *Infrastructure* menu with Clusters, Automation, Bare metal assets
** *Governance* with all policies
** *Applications* with all subscriptions and application sets
** Fleet Virtualization showing all clusters and all VMs

* Now open a new **incognito/private browser window** and navigate to the ACM console:
+
[subs="attributes+"]
----
{openshift_console_url}
----
+
Log in as:
+
** Username: `vm-operator`
** Password: `redhat123`

* Observe the **restricted view** as the `vm-operator` user:
** The *Fleet Virtualization* perspective shows only the clusters and VMs in the `virt-clusters` ManagedClusterSet
** The user can see VM status, access the VM console, and view VM metrics
** The user **cannot** see *Governance* policies, *Infrastructure* node details, or cluster secrets
** The user **cannot** create or delete managed clusters

image::module-07-vm-operator-console.png[VM operator's restricted console view showing only Fleet Virtualization access]

* Click on a VM (e.g., `win2019-install`) and open the *Actions* dropdown to show the available operations:

image::module-07-vm-operator-actions.png[VM operator can Stop Restart Reset and Console into VMs from the Actions menu]

The `vm-operator` user can **Stop**, **Restart**, **Reset**, access the **Console**, and view VM metrics -- exactly the operations granted by the `kubevirt.io:edit` role distributed via the MulticlusterRoleAssignment. They cannot Clone, Delete, or perform Migration actions that require broader permissions.

[TIP]
====
Open the admin console and the vm-operator console side by side to show the contrast. The admin sees the full RHACM feature set; the vm-operator sees only what they need -- Fleet Virtualization for their assigned clusters.
====

* Back in the **Hub terminal** (if disconnected, reconnect with: `{hub_ssh_command}`, password: `{bastion_ssh_password}`), verify the access boundaries with CLI checks:
+
[source,role="execute"]
----
oc auth can-i get nodes --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

+
[source,role="execute"]
----
oc auth can-i get secrets -n openshift-config --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

+
[source,role="execute"]
----
oc auth can-i delete managedclusters --as-group=vm-operators --as=vm-operator
----
+
Expected: `no`

[IMPORTANT]
====
**Key message for the customer:** "This operator can view and manage VMs across the fleet from the console. They can start, stop, restart, and console into any VM on their assigned clusters. But they cannot see a single node, secret, or cluster-level resource. And this permission is centrally managed from the Hub -- if you delete the MulticlusterRoleAssignment, the RBAC disappears from all managed clusters. No more manual Role/RoleBinding management on 50 clusters."
====

== Key Takeaways

* MulticlusterRoleAssignment API replaces ClusterPermission for virtualization RBAC at scale
* Fine-grained RBAC must be enabled in the MultiClusterHub before creating assignments
* Hub-level roles (`acm-vm-fleet:view`) are prerequisites for fleet console access
* Spoke-level roles are distributed via MRA using Placement resources for dynamic cluster targeting
* The ACM console provides a UI for creating and managing role assignments
* VM operators get a full console experience scoped to exactly their responsibilities
* The admin vs. vm-operator console comparison is the most powerful visual in the module
* Group-based subjects mean team membership changes propagate without manifest updates
* Revoking access on the Hub propagates to all managed clusters automatically
