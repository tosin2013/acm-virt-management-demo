== Part 1 -- Inspecting the Topology Graph

=== Know

_Application Topology is the visual proof that everything works together. After deploying VM-based applications via GitOps in Module 1, the topology view shows the complete dependency graph -- which components run where, their real-time status, and how they relate to each other._

**Business Challenge:**
In a multicluster environment, understanding "where is my application running and is it healthy?" requires correlating information across multiple cluster consoles, ArgoCD dashboards, and CLI sessions. This is error-prone and slow.

**Technical Solution:**
RHACM's Application Topology view interprets ArgoCD `Application` and `ApplicationSet` objects to render an interactive graph that:

* Shows all application components across Hub and managed clusters
* Displays real-time status (healthy, degraded, missing)
* Enables remote log retrieval directly from the topology UI
* Works for both container-based and VM-based workloads

**Business Value:**

* Visual validation of GitOps deployments -- see at a glance if everything landed correctly
* Remote diagnostics without kubeconfig access -- fetch logs through the UI
* Cross-cluster dependency mapping -- understand how services connect across clusters

=== Show

NOTE: Ensure you are on the **Hub terminal** and logged into OpenShift. If unsure, run `oc whoami` to verify. If disconnected, reconnect with: `{hub_ssh_command}` (password: `{bastion_ssh_password}`). See xref:02-details.adoc#_connecting_to_clusters[Connecting to Clusters] for full details.

* Open the ACM console at {openshift_console_url} and log in with `{user}` / `{password}` (see xref:02-details.adoc#web-console-login[Logging into the Web Consoles])

* Go to *Applications* in the left navigation

* Observe the list of managed applications -- the `vm-fedora-web` ApplicationSet deployed in Module 1 should be visible

image::acm-applications-list.png[ACM Applications list showing vm-fedora-web]

* Select `vm-fedora-web` to open the topology graph

image::acm-topology-graph.png[ACM Topology graph showing VM components across clusters]

* The topology graph displays:
** The ApplicationSet on the Hub
** The Application instances on each managed cluster
** The VirtualMachine resources and their status
** Associated Services, Routes, and DataVolumes

* Click on a VirtualMachine node in the graph to view:
** Resource details (CPU, memory requests)
** Current phase (Running, Stopped, Migrating)
** Events timeline

* Filter the topology by clicking the search/filter icon and typing `vm-fedora-web` to isolate just this application's components

* Toggle between *Graph view* and *List view* to show different perspectives on the same deployment

== Part 2 -- Fleet Virtualization Management

=== Know

_Beyond the topology graph, RHACM 2.16 introduces a dedicated *Fleet Virtualization* perspective that provides a centralized console for managing VMs across every managed cluster -- without opening individual cluster consoles._

**Business Challenge:**
Operators managing VMs across dozens of clusters need a single pane of glass to see inventory, health, and perform lifecycle actions. Logging into each cluster individually does not scale.

**Technical Solution:**
The Fleet Virtualization perspective combines two data channels:

* *Inventory* -- the `search-collector` agent on each managed cluster streams VirtualMachine metadata to the hub's search index, enabling instant fleet-wide listing
* *Lifecycle controls* -- start, stop, restart, pause, and snapshot actions are proxied through `cluster-proxy` to the managed cluster's KubeVirt API, authenticated via `ManagedServiceAccount` tokens

**Business Value:**

* *Single pane of glass* -- view and manage every VM across the fleet from one console
* *Zero-trust operations* -- operators need hub access only; no kubeconfig or SSH to managed clusters
* *Instant fleet inventory* -- filter, sort, and search VMs by name, cluster, namespace, or node

=== Show

* In the Hub console, click the perspective switcher (top-left) and select *Fleet virtualization*

* The *VirtualMachines* page lists all VMs across managed clusters. You should see both `fedora-web` and `win2019-install` running on the student cluster.

image::fleet-virt-vm-list.png[Fleet Virtualization showing VMs across managed clusters]

* Click the *3-dot menu* next to a VM to see available lifecycle actions:
** Start / Stop / Restart / Pause / Unpause
** Take a snapshot
** Edit YAML

* Use the *Launch links* button to jump directly to:
** VM details page on the managed cluster console
** VM console (VNC)
** Observability metrics in Grafana

* The *Cluster status* section at the bottom shows:
** Total clusters running OpenShift Virtualization
** Total VMs across the fleet
** Cluster utilization and load balance scores

[NOTE]
====
Emphasize to the customer: "You just started, stopped, or inspected a VM running on a remote cluster -- without having any kubeconfig, SSH access, or direct CLI access to that cluster. The ACM Hub proxied everything securely through the cluster-proxy framework."
====

[TIP]
====
You can also search for VMs using the ACM *Search* page (in the Fleet Management perspective). Search for `kind:VirtualMachine` to see all VMs across clusters with rich metadata filtering.
====

== Key Takeaways

* Application Topology provides visual validation of multicluster GitOps deployments
* The view works identically for container and VM-based workloads
* The *Fleet Virtualization* perspective provides centralized VM lifecycle management across all clusters
* Remote VM operations (start/stop/restart/snapshot) work through `cluster-proxy` without per-cluster credentials
* The `search-collector` addon streams VM metadata for instant fleet-wide inventory
* ApplicationSets with `clusterDecisionResource` dynamically target clusters via ACM Placement
* The topology graph spans Hub and managed clusters in a single interactive view
